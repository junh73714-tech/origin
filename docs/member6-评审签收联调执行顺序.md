## 一、你原来的理解 vs 正确理解

### 你原来的理解

```text
第1步：所有人审并签收成员1
第2步：所有人审并签收成员4
第3步：所有人审并签收成员5
第4步：成员4、5互相联调
第5步：所有人审并签收成员6 → 成员6联调
第6步：所有人审并签收成员7 → 联调
第7步：所有人审并签收成员2/3 → 联调
```

### 哪里不对

| 你的想法 | 问题 |
|----------|------|
| 全队先审完成员1，再审成员4… | 太慢；且不是每个人都要深度审成员1 |
| 必须先全员签收4，再全员签收5 | 4和5**可并行**，互不挡 |
| 第4步是「4和5进行联调」 | 主联调是 **成员6 ↔ 4**、**成员6 ↔ 5**，不是4和5互调为主 |
| 等4、5联调完，才开始审成员6 | 成员6的PR**现在就可以被审**；审代码不依赖联调完成 |
| 全员都要对每一人做评审签收 | 不对；**谁依赖谁，谁重点审谁** |

### 正确原则（一句话）

**评审可多人同时做；签收看依赖；签收完立刻和依赖方联调；不要全队排队审同一个人。**

### 第 1 步：成员1 —「环境与公共」就绪（全队前置，但不是全员深度评审）

**不是：** 让 2～7 每个人都把成员1 的代码审一遍并全部点通过。  
**而是：** 成员1 把环境弄好，并把公共规则定清楚；**跟公共改动相关的人**确认即可。

| 动作 | 谁做 | 具体做什么 |
|------|------|------------|
| 部署 | 成员1 | Docker：PG、Redis、MinIO、OpenSearch；给出口令与端口 |
| 迁移 | 成员1 | 至少 `001→002`；说明是否允许成员6再升 `003` |
| 评审（窄范围） | **主要是成员1自己 + 改过公共文件的人**（如成员6改了 BaseModel/config） | 确认迁移不冲突、契约不破坏 |
| 签收 | 成员1 宣布「环境可用」；改公共文件的人得到成员1「公共部分可通过」 | 口头/PR评论即可 |

**成员6 在这一步要做：**

1. 向成员1要 `.env`（勿提交 Git）  
2. 测端口：5432 / 6379 / 9000 / **9200**  
3. 得到「可以 `alembic upgrade head`（含003）」的许可  

**完成标准：**

- [ ] OpenSearch 可连  
- [ ] 成员6 有 `.env`  
- [ ] 成员1 同意跑迁移到 head  

**这一步不过 → 后面真实联调不要硬开。**  
**但：** 不影响你继续做第2步里的「看代码评审」。
