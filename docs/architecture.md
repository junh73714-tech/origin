# 系统架构文档

## 1. 系统概述

### 1.1 项目背景
企业级混合检索 RAG 知识问答平台，支持 Keyword Retrieval、Vector Retrieval、RRF 融合与 Reranker，提供基于证据的 RAG 问答能力。

### 1.2 核心能力
- 用户身份认证与严格权限隔离
- RBAC、数据范围权限和 ABAC
- 知识库、文档、版本、Chunk 与索引管理
- 混合检索：Keyword + Vector + RRF + Reranker
- 基于证据的 RAG 问答、拒答和来源引用
- 标准问答生成、审核、发布、失效与版本联动
- 用户反馈、知识缺口发现、检索调试和效果评估
- 完整审计日志与安全监控

### 1.3 技术栈

| 层级 | 技术选型 |
|------|----------|
| 后端框架 | Python 3.10+ / FastAPI / SQLAlchemy 2.x |
| 数据库 | PostgreSQL + pgvector |
| 搜索引擎 | OpenSearch (Keyword Retrieval) |
| 缓存 | Redis |
| 消息队列 | Celery (基于 Redis) |
| 对象存储 | MinIO |
| 前端框架 | React 18 / TypeScript / Vite / Ant Design |
| 状态管理 | Zustand |
| 部署 | Docker Compose / Nginx / Prometheus / Grafana |

## 8. 关键设计决策

### 8.1 为什么采用模块化单体
- 一期项目规模适中，无需微服务复杂度
- 便于团队协作和代码共享
- 降低部署和运维复杂度
- 未来可平滑拆分为微服务

### 8.2 为什么 PostgreSQL 是事实来源
- 所有业务状态最终一致性保障
- 事务支持保证数据完整性
- OpenSearch 和 pgvector 是派生索引
- 便于审计和回溯

### 8.3 为什么使用 RRF (Reciprocal Rank Fusion)
- 平衡 Keyword 和 Vector 检索结果
- 无需额外训练，部署简单
- 对长尾查询有良好支持

### 8.4 为什么使用 Outbox 模式
- 保证跨模块事件一致性
- 避免分布式事务复杂度
- Redis 作为 Celery broker 已有基础设施

### 8.5 权限服务为何必须唯一
- 集中管理避免权限冲突
- 简化审计和合规
- 统一缓存提升性能
