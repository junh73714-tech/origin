## 2024-01-15: 采用模块化单体架构

**问题**: 如何在保持团队协作效率的同时，确保系统可扩展性和可维护性？

**选项**:
- 选项 A: 微服务架构 - 每个模块独立部署
- 选项 B: 模块化单体 - 单仓库单部署，按模块组织代码
- 选项 C: 插件化架构 - 动态加载模块

**决定**: 模块化单体 (选项 B)

**理由**:
- 一期项目规模适中，无需微服务的复杂度
- 便于团队成员共享代码和协作
- 降低部署和运维复杂度
- 统一的数据库便于数据一致性和审计
- 未来可平滑拆分为微服务

**影响**:
- 所有模块共享同一 PostgreSQL 实例
- 通过包结构和命名约定隔离模块边界
- 数据库迁移需要协调

## 2024-01-15: PostgreSQL 作为唯一事实来源

**问题**: 如何确保业务状态的一致性和可审计性？

**选项**:
- 选项 A: PostgreSQL 作为唯一数据源，Elasticsearch/pgvector 仅作为索引
- 选项 B: 每个服务使用独立数据库，通过事件同步
- 选项 C: 使用分布式数据库如 CockroachDB

**决定**: 选项 A

**理由**:
- PostgreSQL 提供强一致性和事务支持
- 简化开发和调试复杂度
- 便于审计和合规要求
- OpenSearch 和 pgvector 是派生数据，可重建
- 降低运维复杂度

**影响**:
- 所有状态变更必须通过 PostgreSQL 事务
- 索引服务失败不影响核心业务
- 数据重建流程必须可用

## 2024-01-15: 使用 OpenSearch + pgvector 混合检索

**问题**: 如何平衡关键词精确匹配和语义相似度检索？

**选项**:
- 选项 A: 仅使用 Elasticsearch
- 选项 B: 仅使用 pgvector
- 选项 C: OpenSearch + pgvector + RRF 融合

**决定**: 选项 C

**理由**:
- OpenSearch 擅长关键词精确匹配，支持复杂查询
- pgvector 擅长语义相似度检索
- RRF (Reciprocal Rank Fusion) 融合两者结果
- 无需额外训练，部署简单
- 对长尾查询有良好支持

**影响**:
- 需要维护两套索引
- 融合参数需要调优
- 索引构建时间增加

## 2024-01-15: 使用 Outbox 模式进行跨模块事件传递

**问题**: 如何在不使用独立消息队列的情况下实现跨模块事件传递？

**选项**:
- 选项 A: 使用 Kafka/RabbitMQ 等消息队列
- 选项 B: 使用数据库 Outbox 表 + 轮询
- 选项 C: 直接在业务代码中调用其他模块

**决定**: 选项 B

**理由**:
- 复用现有 Redis 作为 Celery broker
- Outbox 模式保证事件必定发送
- 事务内写入，避免不一致
- 实现简单，易于理解和维护

**影响**:
- 事件处理有延迟（轮询间隔）
- 需要处理幂等性
- 事件顺序不保证

## 2024-01-15: 权限服务唯一性

**问题**: 如何处理跨模块的权限检查？

**选项**:
- 选项 A: 每个模块独立实现权限检查
- 选项 B: 统一的权限服务，所有请求经过它
- 选项 C: 权限检查逻辑下沉到数据库层

**决定**: 选项 C + 统一权限服务

**理由**:
- 权限逻辑集中管理，避免重复和冲突
- 通过 AccessContext 在请求级别传递权限信息
- 数据库层使用 RLS (Row Level Security) 加强防护
- 检索前过滤保证安全性

**影响**:
- 成员4负责权限核心逻辑
- 其他成员通过 AccessContext 使用权限
- 需要协调权限变更

## 2024-01-15: 文档版本变更联动缓存失效

**问题**: 文档更新后如何保证检索结果的一致性？

**选项**:
- 选项 A: 实时删除相关缓存
- 选项 B: 使用版本号，缓存键包含版本
- 选项 C: 文档变更后标记索引为过期，下次检索时重建

**决定**: 选项 B

**理由**:
- 版本号变更自动使缓存失效
- 无需额外的缓存清理逻辑
- 便于追踪文档历史
- 简化实现

**影响**:
- 索引任务需要记录文档版本
- 旧版本缓存自然过期即可
- 内存占用略有增加

## 2024-01-15: 标准问答必须审核后才能发布

**问题**: 如何保证上线问答的质量？

- 选项 A: 直接上线，依赖用户反馈迭代
- 选项 B: 必须审核通过才能发布

**影响**:

- 需要审核记录表
- 发布和下线需要记录原因

## 2024-01-15: 使用 Celery 处理异步任务

**问题**: 如何处理文档解析、索引等耗时操作？

**选项**:
- 选项 A: 使用 FastAPI 的 BackgroundTasks
- 选项 B: 使用 Celery + Redis
- 选项 C: 使用 asyncio 协程

**决定**: 选项 B

**理由**:
- Celery 是 Python 生态最成熟的异步框架
- 支持任务重试、优先级、监控
- Redis 已在基础设施中
- 支持分布式部署

**影响**:
- 需要启动 Celery Worker
- 任务状态需要持久化
- 与主应用共享 Redis

## 2024-01-15: 使用 JWT 实现无状态认证

**问题**: 如何实现高效的用户认证？

**选项**:
- 选项 A: Session + Redis 存储
- 选项 B: JWT 无状态令牌
- 选项 C: OAuth2 + OIDC

**决定**: 选项 B

**理由**:
- JWT 无需服务端存储会话
- 便于水平扩展
- 支持短期 Access Token + 长期 Refresh Token
- 业界标准方案

**影响**:
- Token 刷新需要前端配合
- 登出需要处理 Token 黑名单
- Token 泄露风险

## 2024-01-16: 使用 MinIO 作为对象存储

**问题**: 如何存储用户上传的文档？

**选项**:
- 选项 A: 直接存储在服务器文件系统
- 选项 B: 使用 MinIO (S3 兼容)
- 选项 C: 使用云存储 (AWS S3 / 阿里云 OSS)

**决定**: 选项 B

**理由**:
- S3 兼容 API，便于未来迁移
- 部署简单，支持 Docker
- 提供版本控制、生命周期等企业功能
- 本地开发和生产环境一致

**影响**:
- 需要额外部署 MinIO
- 配置 S3 兼容的 Access Key/Secret Key
- 文件路径需要规范化
